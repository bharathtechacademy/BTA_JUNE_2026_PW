Original Jira Story

Description: As an existing user, I want to log in to my Creatio CRM account using my business email and password through a secure and well-designed form.

Acceptance Criteria:

ü  The form should have a header with the title "LOG IN TO YOUR ACCOUNT".

ü  Fields required for login include " Business email" , " Password" textboxes along with label on top of each textbox and ‘LOG IN’ button.

ü  Password textbox should have ‘eye’ icon to display the password entered in textbox

ü  Provide "Forgot password" link to reset the password on top of Password textbox

ü  Below ‘LOG IN’ button add label ‘or log in using’ to login with other options

ü  LinkedIn, Google, and Facebook logo’s should be added as icons with hyperlink below ‘LOG IN’ button along with labels.

ü  Below social media icons add label ‘Don’t have an account?’ to create new account

ü  Add ‘SIGN UP’ link to create new account below the label ‘Don’t have an account?’

ü  Add ‘cookie settings’ icon without label to change consent at the bottom left corner to view, withdraw, change cookie consent settings.

ü  Add ‘creatio chatbot’ icon without label to help customers FAQ’s at the bottom right corner.

Detailed Requirement Analysis

Story Objective & Business Goals

The story aims to allow an existing Creatio CRM customer to sign in with a business email and password through a secure, polished form. The user experience is expected to support both standard credential login and alternate SSO choices, while preserving account creation and privacy management controls.

Primary personas: Existing business customers, sales/operations users, and returning users who are already registered within the Creatio CRM ecosystem.

Business value: reduces friction for returning users, offers trust-building UX elements, supports conversion to account creation, and provides quick access to support or consent management.

Business Scope & User Workflow

  • User lands on the login screen.
  • User enters business email and password.
  • User optionally reveals the password using an eye icon.
  • User accesses password recovery via forgot password.
  • User clicks login using credentials or social identity providers.
  • If no account exists, entry to sign-up flow is available.
  • User can manage cookie settings and access FAQ chatbot.

Business Rules & Functional Logic

Core Rules

  • Business email and password are the primary login inputs.
  • The login form must include a header titled “LOG IN TO YOUR ACCOUNT”.
  • Each field must include an explicit label placed above the control.
  • The password field must allow visibility toggling with an eye icon.
  • Forgot password must be placed above the password field.
  • Social sign-in options appear under the main login action.
  • New account registration must be available from the login page.
  • Cookie settings and chatbot controls must remain visible without obstructing core login actions.

Conditional Logic / State Behavior

  • If the user enters valid credentials, they proceed to authenticated access.
  • If the password is hidden, the eye icon toggles to reveal the value.
  • If the user chooses social login, they are routed to the linked provider identity flow.
  • If the user does not have an account, the sign-up link leads to registration.
  • If the user requests password reset, they proceed to forgot-password workflow.
  • If the user clicks cookie settings, they can view/update consent preferences.
  • If the user opens FAQ assistance, chatbot should provide support or navigation to FAQ topics.

Inputs, Outputs, Validations & Error Handling

Expected Inputs

  • Business email: required, likely in email format, must match a corporate or business domain pattern.
  • Password: required, masked by default, hidden text toggled by eye icon.
  • Social provider selection: LinkedIn, Google, Facebook as clickable icon links.
  • Consent toggles for cookies: view, withdraw, change consent settings.

Likely Validation & Error Handling

  • Incomplete email or password should prevent login action and show a clear validation message.
  • Invalid email format should trigger inline validation or server-side rejection.
  • Incorrect credentials should display a generic authentication failure message.
  • Rate limiting or account lockout should be handled gracefully without exposing sensitive account state.
  • Failed social login should return to the login page with a recoverable error state.

Edge Cases & Alternate Flows

Negative and Boundary Scenarios

  • Empty email and password fields.
  • Malformed email with spaces, Unicode, or unsupported domain syntax.
  • Minimum/maximum password length not defined by story and must be clarified.
  • Password visibility toggled while field contains special characters or long values.
  • Cross-site scripting payloads in email or password fields.
  • Session timeout or stale auth token on return to login.

Alternate Flows

  • Reset password via forgot-password.
  • Social login via LinkedIn, Google, or Facebook.
  • Sign-up route from the login page.
  • Cookie consent management from floating icon.
  • Chatbot assistance access from floating icon.
  • Back button behavior after authentication or after password reset.

Assumptions & Open Questions

Assumptions by QA

  • The login form is a front-end page integrated with the authentication service.
  • Passwords are masked by default and must be toggleable without losing entered content.
  • The social media icons are static links to provider-based sign-in flows.
  • Cookie settings and chatbot icons are floating UI elements that do not prevent login usability.

Open Questions for PO / BA / Tech Lead

  • What are the exact validation rules for business email format and password policy?
  • Should social login be fully functional OAuth or placeholder links for this story?
  • What should happen after clicking Forgot Password: redirect to a reset page or a modal?
  • Is the cookie settings feature required to be a full consent management workflow or just a persistent settings entry point?
  • Should the chatbot icon navigate to FAQ content, a live support chat, or just a static FAQ page?

Risks & Dependencies

  • Third-party SSO: LinkedIn, Google, and Facebook integrations must be configured, and failure states need clear handling.
  • Authentication service: login success/failure responses determine UX and security behavior.
  • Privacy compliance: cookie settings must align with consent requirements and platform policies.
  • Accessibility: icons, labels, and focus states must satisfy keyboard and screen-reader expectations.
  • Responsive design: the floating widgets and form layout must remain usable across desktop, tablet, and mobile viewports.

Functional Test Plan

Objectives & Scope

In Scope: login form layout, validation, password visibility toggle, forgot password link, social login UI, sign-up CTA, cookie settings, chatbot, and responsive behavior.

Out of Scope: backend identity provider configuration, database migration, performance benchmarking, and unrelated CRM modules.

Approach

Cross-browser UI automation via Playwright Page Object Model, with targeted API validation for expected authentication responses and error handling. Positive, negative, boundary, and state/UX validations will be covered.

Test Data Strategy

  • Valid business email and password for successful login.
  • Invalid email and wrong password for negative tests.
  • Empty field values and long strings for boundary tests.
  • Predefined SSO account personas for LinkedIn, Google, and Facebook.

Environment & Entry/Exit Criteria

  • Browsers: Chromium, Firefox, WebKit.
  • Viewports: 1920x1080, 768x1024, 375x667.
  • Entry: Story ready for test, login page available, test data provisioned.
  • Exit: all scenarios executed, no open critical/high defects, RTM completed.

Missing Requirements, Gaps & Final Testing Observations

  • The story does not define exact email validation rules, including accepted domain patterns or business-email-only enforcement.
  • No password policy is specified: min/max length, allowed characters, or account lockout thresholds are missing.
  • There is no explicit requirement for inline validation text, error styling, or disabled login state before form validation passes.
  • Exact requirements for social login are unclear: whether they are full SSO integrations or visual placeholders.
  • Forgot password, cookie settings, and chatbot flows are implied but not specified in process detail or success criteria.
  • Accessibility labels and keyboard navigation are not defined but are essential for compliance and UX quality.

QA Recommendation: request clarification from the PO or product owner on validation rules, social login implementation scope, cookie consent behavior, and chatbot route flow before code sign-off. This will reduce defect risk in the login module and improve testability.
