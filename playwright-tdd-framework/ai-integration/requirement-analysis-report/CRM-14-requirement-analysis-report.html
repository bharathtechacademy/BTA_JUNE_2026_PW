1 Original Jira Story (Verbatim)

Jira Source: CRM-14
Extracted via Jira REST API v3

Description: As an existing user, I want to log in using my LinkedIn, Google, or Facebook accounts to quickly access my account without manually entering credentials.

Acceptance Criteria:

Social media icons and buttons for LinkedIn, Google, and Facebook should be available with appropriate styling.

Clicking a button should redirect to the OAuth authentication flow of the provider.

Upon successful authentication, the user should be logged in and redirected to their dashboard.

Display error messages for any failures during the login process.

2 Detailed Requirement Analysis

Analysis Depth: Comprehensive

Story Objectives & Business Value

Primary Objective: Implement single sign-on (SSO) authentication enabling returning and existing users to authenticate with trusted identity providers (LinkedIn, Google, Facebook) seamlessly without manually typing email and password credentials.

Business Value & KPIs:

  • Reduced Login Friction: Lowers cognitive load and login drop-off rates by enabling one-click or two-click authentication.
  • Reduced Credential Support Overhead: Minimizes password reset requests, locked accounts, and forgotten credential tickets.
  • Enhanced Security Posture: Delegates authentication to tier-1 identity providers supporting multi-factor authentication (MFA/2FA) and device risk analysis.

Target Personas:

  • Existing Corporate User: Uses Google Workspace or LinkedIn credentials matching their CRM registration.
  • Social / Consumer User: Uses personal Facebook or Google account.
  • Mobile / Tablet User: Benefits significantly from touch-based single-tap OAuth flows without keyboard typing.

Business Scope & User Workflows

Supported Identity Providers:

Google (OAuth 2.0 / OpenID Connect) LinkedIn (OAuth 2.0 / Sign In with LinkedIn) Facebook (Facebook Login / Graph API)

End-to-End User Journey:

  1. Discovery: User visits the CRM login screen (integrated below the primary login button as defined in CRM-12).
  2. Selection: User clicks their chosen social provider button (e.g., "Sign in with Google").
  3. Redirection: The application generates a secure OAuth state token and redirects to the provider's authorization endpoint.
  4. Provider Consent / Login: User enters credentials (if not already logged into provider) and grants authorization.
  5. Callback: Provider redirects to CRM OAuth callback endpoint with an authorization code and state token.
  6. Token Exchange & Session Creation: CRM backend exchanges the authorization code for tokens, retrieves verified user profile, sets session cookies/JWT, and creates active session.
  7. Dashboard Landing: User lands on the CRM Dashboard with verified authenticated state.
  8. Failure / Cancellation Route: User sees clear, actionable error toast or banner on login page without infinite loops or blank pages.

3 Business Rules & Functional Logic

6 Formal Business Rules

UI Presentation & Provider Branding Rules

  • BR-01 (Provider Branding Compliance): Each social button must strictly follow provider visual identity standards:
    • Google: Neutral white or dark container, official multi-color "G" logo, proper typography ("Sign in with Google").
    • LinkedIn: Official LinkedIn Blue background (#0A66C2) with official white "in" glyph.
    • Facebook: Official Facebook Blue (#1877F2) with official white "f" glyph.
  • BR-02 (Interactive State Requirements): Buttons must have clear hover states, focus outlines for keyboard navigation (Tab/Shift+Tab), active pressed states, and accessible ARIA attributes (e.g., aria-label="Log in with Google").
  • BR-03 (Layout Position): Social login options must reside in the dedicated section below the standard login action button, aligned with the CRM-12 layout.

Authentication, Security & State Logic

  • BR-04 (OAuth 2.0 Authorization Code Flow): Authentication must use the Authorization Code Flow with PKCE (Proof Key for Code Exchange) or secure server-side exchange. Client secrets must never be exposed to the browser.
  • BR-05 (CSRF State Protection): Every OAuth initiation must generate a cryptographically strong, non-guessable state parameter bound to the user's session. The callback must strictly reject mismatched or missing state parameters.
  • BR-06 (Account Binding & Redirection):
    • When the OAuth email matches an existing verified CRM user, the account is securely linked and logged in.
    • Upon successful authentication, user is redirected to /dashboard (or the intended protected URI requested prior to login).
    • If the user cancels or denies consent, the callback redirects back to login with a user-friendly failure notice.

4 Inputs, Outputs, Validations & Error Handling

Input / Output Specification

Inputs & Outputs Matrix

User & System Inputs:

  • User click / activation of Provider Button (Google, LinkedIn, or Facebook).
  • OAuth consent grant or cancellation on provider dialog.
  • Callback query parameters: code (authorization code) and state (CSRF token).
  • Provider error parameters: error=access_denied, error_description.

System Outputs:

  • Browser redirect to provider OAuth URI with client_id, redirect_uri, response_type=code, scope, and state.
  • Authenticated session tokens (HTTP-only, Secure, SameSite cookies or JWT).
  • Final navigation to /dashboard.
  • User-facing localized error alerts on authentication failure.

Error Scenarios & Messaging Specifications

User Denied / Cancelled Consent:
Condition: User clicks "Cancel" or closes provider authorization modal.
Behavior: Returns to /login; Displays: "Social login was cancelled. Please try again or use your email and password."

Mismatched CSRF State Parameter:
Condition: Incoming state does not match session store (potential replay or CSRF attack).
Behavior: Reject token exchange, log security event; Displays: "Your session has expired or is invalid. Please start the login process again."

Provider Outage / Network Timeout:
Condition: Identity provider API fails or returns HTTP 500/503/504.
Behavior: Graceful retry prompt; Displays: "Unable to connect to [Provider]. Please try again later or sign in with your email."

5 Edge Cases & Alternate Flows

Resilience & Boundary Scenarios

Security & Protocol Edge Cases

  • Replay Attack on Authorization Code: Attempting to reuse an already-exchanged OAuth authorization code must fail with HTTP 400 Bad Request.
  • Unverified Email Address: Provider returns a profile where email_verified = false. System must prevent automatic account takeover.
  • Missing Public Email Permission: Facebook or LinkedIn user restricts email scope permission. Application must prompt user that email is required for CRM account association.
  • Rapid Multi-Clicking: User rapidly double-clicks provider button. System must debounce to prevent spawning duplicate OAuth requests.
  • Session Inactivity during Provider Login: User stays on Google login page for 30 minutes before completing. System must handle stale session gracefully.

User Experience & Alternate Flows

  • Deep Linking / Relay State: User attempts to visit /contacts/create, gets redirected to login, uses Google Login, and is correctly redirected to /contacts/create instead of default dashboard.
  • Browser Back Button during Redirect: User hits browser back button after being redirected to provider. System should return to stable login page without broken state.
  • Popup Blockers (if popup mode): If OAuth opens in popup and is blocked by browser, app should fall back gracefully to full-page redirect or display prompt.
  • Responsive Viewports & Touch Targets: On mobile devices (375px width), buttons must maintain minimum 44x44px touch targets without overlapping or truncation.

6 Assumptions & Open Questions

Requires Stakeholder Alignment

Assumptions Made by QA

  • Existing Account Mapping: QA assumes accounts are mapped primary by verified email address returned in the OAuth profile.
  • Full-Page Redirection: QA assumes the OAuth flow operates via full-page HTTP redirection (standard web flow) rather than in-page popups, unless specified otherwise.
  • Default Landing: QA assumes successful authentication routes to the standard /dashboard route.
  • Provider Sandboxes: Staging / QA environments have sandbox OAuth client credentials configured for Google, LinkedIn, and Facebook.

Open Questions for PO / Tech Lead

  1. Unregistered Social Users: When a user logs in via Google/LinkedIn/Facebook for the first time without an existing CRM account, should the system:
    (A) Auto-create a new CRM account?
    (B) Block login with message "No account found. Please sign up first"?
    (C) Route to sign-up page pre-filled with social profile data?
  2. Account Linking Confirmation: If an existing password user clicks "Sign in with Google" for the first time, should we require one-time password entry to confirm account linking?
  3. Requested OAuth Scopes: What specific scopes are being requested? (Recommended: Google: openid email profile, LinkedIn: openid profile email, Facebook: public_profile, email).
  4. Social Account Unlinking: Where can users view or unlink connected social accounts in their profile settings?
  5. Session Lifetime: Do social login sessions follow the standard CRM session timeout policy (e.g., 30 minutes inactivity) or provider token expiry?

7 Risks & Dependencies

Risk Mitigation Analysis

External & Technical Dependencies

  • Third-Party OAuth Availability: Dependence on Google Identity, LinkedIn Developer Portal, and Meta Graph API operational uptime.
  • Provider API Versioning & Deprecation: Identity providers periodically deprecate OAuth endpoints (e.g., Google Sign-In library migration to GIS, LinkedIn v1 to v2/OIDC).
  • OAuth Client Secrets & Redirect URIs: Accurate configuration of authorized redirect URIs in each provider's developer console for localhost, staging, and production.

Security & Compliance Risks

  • Account Takeover via Unverified Email: Risk of malicious user claiming someone's account using an unverified social identity. Mitigated by enforcing email_verified flag checks.
  • CSRF Token Vulnerability: Failure to strictly validate state could allow attackers to bind their social account to a victim's session.
  • Brand Guideline Violations: Rejection or takedown of OAuth credentials if buttons fail Google, LinkedIn, or Meta trademark display rules.

8 Functional Test Plan

Strategy: Playwright POM Automation

Objectives & In-Scope vs Out-of-Scope

Objectives: Validate the end-to-end functionality, security, responsiveness, error resilience, and visual compliance of social login integrations across all target browsers and platforms.

In-Scope:

  • Social login button layout, styling, icons, labels, hover/focus states.
  • OAuth authorization URL generation, parameters (client_id, scope, state, redirect_uri).
  • OAuth callback processing, token verification, session creation.
  • Navigation to dashboard and deep-linked routes.
  • Error handling (cancellation, network failure, CSRF mismatch, unlinked user).
  • Cross-browser (Chromium, Firefox, WebKit) and multi-viewport testing.

Out-of-Scope: Performance stress testing of provider servers, internal backend provider authentication algorithms, biometric authentication on physical devices.

Test Approach, Environment & Criteria

Test Approach:

  • UI E2E Automation: Playwright Page Object Model covering UI components, interactions, and full-path navigation.
  • API & Callback Mocking: Use Playwright page.route() to stub provider callback parameters (simulating access_denied, corrupted state, server 500s) for deterministic testing.
  • Sandbox Account Verification: Dedicated test accounts on Google Sandbox, LinkedIn Developer App, and Facebook Test Users.

Environment & Browsers:

  • Browsers: Chromium, Firefox, WebKit.
  • Viewports: Desktop (1920x1080), Tablet (768x1024), Mobile (375x667).

Entry & Exit Criteria:

  • Entry: CRM login page deployed; OAuth client IDs provisioned; mock routes configured.
  • Exit: 100% test scenarios executed; 0 Critical/High defects open; 100% RTM coverage.

11 Missing Requirements, Gaps & Final QA Observations

QA Sprint Recommendations

Identified Specification Gaps

  • G-01: Behavior for Unregistered Social Users: The acceptance criteria do not define what happens when a user attempts social login with an email not yet registered in the CRM. The team must confirm whether to auto-provision an account or redirect to registration.
  • G-02: Missing Email Scope Permission: If a user selectively unchecks the email permission on Facebook or LinkedIn consent dialog, the CRM cannot map the account. A dedicated error state or permission retry prompt must be specified.
  • G-03: Multiple Social Accounts with Different Emails: If a user has a Google account with alice@gmail.com and a LinkedIn account with alice@work.com, they will create two distinct accounts unless a manual account merging feature is supported.
  • G-04: Session Expiration & Token Refresh: The story does not document token refresh mechanics or whether CRM session expiry is decoupled from third-party OAuth token expiration.

QA Architecture Recommendations for Sprint Delivery

  1. Incorporate Mock OAuth Fixtures in Playwright: Since testing live third-party OAuth login screens in CI/CD triggers CAPTCHAs, bot blocks, and MFA, the automation framework should implement Playwright network route mocking (page.route('**/oauth/callback*', ...)) for automated test suites, reserving live credentials for staging smoke tests.
  2. Enforce Explicit Branding Checks: Verify that official SVG vector assets are utilized rather than raster images to prevent blurry icons on high-DPI (Retina) screens.
  3. Security Review on Token Handling: Ensure authorization codes and tokens are strictly exchanged over HTTPS, and that sensitive session cookies are flagged with HttpOnly, Secure, and SameSite=Lax.
